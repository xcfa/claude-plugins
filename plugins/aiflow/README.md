# aiflow

Плагин Claude Code, который ведёт пачку задач через конвейер «план → реализация →
AI-ревью DeepSeek → мерж в `master`» в фоновых сессиях Claude Code. Вы пишете
задачи одним сообщением оркестратору, обсуждаете планы в PR или в сессии
планировщика, одобряете их — дальше всё идёт само. Очередь, лимиты, порядок ревью
и перезапуски ведёт программа `aiflow`, а не модель: она работает отдельной службой,
а о том, что требует вашего решения, сообщает системными уведомлениями и в панели.

## Что внутри

| Компонент | Что делает |
| --- | --- |
| `agents/orchestrator.md` | Интерфейс: принимает задачи, отвечает о состоянии, реагирует на события |
| `agents/planner.md` | Opus: оценка задачи, поручение исполнителю или «сделаю сам». Правила плана и разговора вынесены в `prompts/planner-plan.md` и `prompts/planner-talk.md` — планировщик читает их, только когда они нужны |
| `agents/worker.md` | Исполнитель: реализация по плану, цикл ревью в свою очередь. Модель — по оценке планировщика: Haiku, Sonnet или Opus |
| `agents/explorer.md`, `agents/researcher.md` | Haiku: ответы на конкретные вопросы к коду и документации |
| `skills/intake` | `/aiflow:intake <задачи>` — разбор и постановка в очередь, запуск монитора |
| `skills/resume` | `/aiflow:resume` — поднять службу после перезагрузки |
| `skills/discuss` | `/aiflow:discuss <PR>` — обсудить план в свежей сессии |
| `skills/ui` | `/aiflow:ui` — открыть панель в браузере |
| `monitors/monitors.json` | `aiflow run --events` в сессии оркестратора: поднять службу, ответы на вопросы в чат |
| `hooks/hooks.json` | Проверка среды при старте сессии (только в подготовленных репозиториях); доставка дополнений работающей сессии |
| `bin/aiflow` | Диспетчер и подкоманды; в PATH Bash-команд сессий |
| `scripts/review.py` | Один раунд ревью: CI-гейт, защищённые пути, DeepSeek, inline-ревью, автомерж |
| `scripts/ui.html` | Панель: что ждёт вас, доска задач по стадиям, события |

## Требования

Claude Code с agent view (`claude agents` открывает полноэкранный список), Python 3.9+,
`git`, `gh` (авторизован), `opencode` с подключённым DeepSeek. Отдельный бот-аккаунт GitHub
нужен только в режиме `review_identity: bot` (см. ниже).

## Установка

```bash
claude plugin marketplace add /путь/к/aiflow-marketplace
claude plugin install aiflow@aiflow-local
```

Если храните маркетплейс в git, закоммитьте исполняемый бит: `git update-index --chmod=+x plugins/aiflow/bin/aiflow`.

## Подготовка репозитория (один раз)

1. **Чей аккаунт.** По умолчанию (`review_identity: self`) ревью и мерж идут от вашего `gh`:
   ревью публикуется комментарием (одобрить свой PR GitHub не даёт), мержит `review.py`
   после вердикта approve и зелёного CI. Если нужна жёсткая граница — GitHub сам требует
   одобрение, — поставьте `review_identity: bot` и заведите бота: fine-grained token на
   репозиторий (Contents, Pull requests, Issues — read/write) в `~/.config/ai-review/token`
   или в `REVIEW_BOT_TOKEN`.
2. **GitHub.** Промежуточной ветки нет: одобренные PR мержатся сразу в `master`
   (`base_branch` в `.aiflow/config.json`). Settings → General: Allow squash merging.
   Защита `master` — по желанию (в приватных репозиториях на бесплатном плане её нет):
   PR, обязательные проверки из `ci.yml`, «Require branches to be up to date», Allow auto-merge;
   обязательное одобрение — только в режиме `bot`. CODEOWNERS и «Require approval of the most
   recent push» не включайте.
3. **Инициализация.** В сессии Claude Code в корне репозитория: `! aiflow init`. Команда
   создаст `.aiflow/config.json`, шаблоны `.github/workflows/ci.yml`,
   `docs/ARCHITECTURE.md`, добавит права для фоновых сессий в `.claude/settings.json`
   и метки `plan-approved`, `needs-human`, `retry`.
4. **Настройка.** Выберите модель ревьюера в панели («Настройки» внизу страницы) или впишите
   `reviewer_model` в `.aiflow/config.json` (`opencode models deepseek`),
   при желании положите свои инструкции ревьюера в `.opencode/aiflow-reviewer.md` (по умолчанию —
   `templates/reviewer.md` плагина; aiflow запускает его агентом `aiflow-reviewer` через отдельный
   конфиг opencode, так что он не пересекается с агентами проекта),
   заполните `ci.yml`, добавьте в `.claude/settings.json` allow-правила для сборки и тестов
   проекта (иначе фоновые сессии будут ждать вашего разрешения). Закоммитьте всё, кроме `.aiflow/`.
5. **Доверие к папке.** Хотя бы раз откройте `claude` в репозитории интерактивно и примите
   доверие — иначе фоновые сессии не стартуют.
6. **Проверка.** `! aiflow doctor`.

Чтобы вызывать `aiflow` из обычного терминала, добавьте в PATH каталог `bin` плагина
(путь показывает `claude plugin list`, строка «Read from»).

## Работа

1. Откройте сессию оркестратора (очередь ведёт служба aiflow, так что закреплять сессию
   не обязательно; закреплённая не засыпает и сразу пересказывает события):
   ```bash
   claude --bg --agent aiflow:orchestrator --name aiflow "Готов к задачам"
   claude agents     # выделите строку aiflow, Ctrl+T, затем Enter
   ```
2. В этой сессии: `/aiflow:intake 1) экспорт отчётов в CSV 2) починить пагинацию в API …`
3. Монитор сообщит, когда планы будут готовы. Обсуждайте план в PR (комментарием —
   планировщик проснётся сам), в сессии планировщика (`claude attach <id>`) или через
   `/aiflow:discuss <PR>`. Одобрение — метка `plan-approved`, кнопка в панели
   или `! aiflow approve <id>`.
4. Реализация и ревью идут без вас. PR с общими файлами ревьюятся по одному, с rebase на
   свежий `master`; одновременно — только PR без общих файлов (`review_concurrency`). Мерж всегда
   по одному и только из ветки, которая не отстаёт от `master`.
5. При «нужен человек» оркестратор объяснит причину. Повтор — `aiflow retry <id>`,
   метка `retry` или кнопка в панели. Повтор сначала возобновляет ту же сессию (с её контекстом
   и незакоммиченными правками) в той же стадии; новая сессия запускается, только если возобновить
   не удалось. Можно и ответить самой сессии (дать доступ, «всё норм»): когда она снова
   заработает или пришлёт отчёт, монитор сам вернёт задачу в её стадию.
6. Одобренные PR с зелёным CI сами уходят squash-мержем в `master`. Проверьте `master`
   после мержей; найденное — новой пачкой через `/aiflow:intake` или `git revert`.

### Служба и несколько проектов

Очереди ведёт служба aiflow: один фоновый процесс на пользователя для всех проектов из
`~/.aiflow/projects.json`. От сессий Claude она не зависит: закрытие сессии оркестратора её
не останавливает. Проект попадает в службу при `aiflow init` или `aiflow up` в его каталоге;
монитор сессии оркестратора (`/aiflow:intake`, `/aiflow:resume`) сам поднимает службу, если её нет,
и перезапускает её, если она старше установленной версии плагина, а сам только пересказывает
события своего проекта в чат.

```bash
aiflow up               # запустить службу и добавить в неё текущий проект
aiflow up --autostart   # и запускать службу при входе в систему (--no-autostart — выключить)
aiflow projects         # проекты службы, её версия и адрес панели
aiflow forget [путь]    # убрать проект из службы (задачи и PR не трогаются)
aiflow down             # остановить службу; фоновые сессии Claude продолжат работать
```

После перезагрузки машины с автозапуском ничего делать не нужно; без него — `aiflow up`
или `/aiflow:resume` в сессии оркестратора. В сессии, продолженной через `claude --resume`,
Claude Code монитор плагина повторно не запускает: `/aiflow:resume` поднимает только службу
(`aiflow up`), и ответы на вопросы в чат такой сессии сами не приходят — спросите оркестратора.
Автозапуск берёт самую новую установленную версию плагина из того же маркетплейса. `aiflow down`
останавливает службу, пока вы сами не запустите её снова: мониторы сессий её не поднимают. Порт общей панели — `ui_port`
в `~/.aiflow/config.json` (8765 по умолчанию, `0` — без панели).
Сессии, которые остановились или пропали (перезагрузка, закрытие), монитор возобновляет сам —
один раз подряд (`auto_resume` в `.aiflow/config.json`, `0` — выключить); если сессия снова
останавливается без продвижения, задача уходит в «нужен человек». Сессию, остановленную вами
намеренно, монитор тоже поднимет: чтобы задача не продолжалась, поставьте очередь на паузу
или закройте PR.

О том, что ждёт вас, сообщает служба — системными уведомлениями (Windows, macOS, Linux
с `notify-send`) и в панели: план готов или обновлён, есть ответ на вопрос, сессия ждёт ответа,
нужен человек, смержено, пауза и её снятие, ошибки, пачка завершена. Выключить уведомления —
`desktop_notify: false` в `.aiflow/config.json`.

Оркестратору монитор по умолчанию пишет (и тем самым будит его, а это токены) только ответ на ваш
вопрос (`kind: ask`). Об остальном оркестратор скажет, когда вы ему напишете: на любое сообщение он
сначала смотрит `aiflow status`. Настройка `notify` в `.aiflow/config.json`: `answers` (по умолчанию);
`important` — всё, что ждёт вас, и снятие задачи; `all` — все события; `none` — ничего.

## Панель

Её держит служба: `http://127.0.0.1:8765/`. `aiflow ui --open --detach` (или `/aiflow:ui`) поднимает
службу, если нужно, и открывает панель отдельным окном (режим приложения Edge или Chrome, иначе
вкладка браузера). Панель слушает только loopback, действия защищены токеном страницы.

Разделы панели, сверху вниз:

- **Ждут вас** — задачи всех проектов, которым нужно ваше решение. У «нужен человек» — причина и строка
  «Что сделать». Кнопки: одобрить план, повторить, открыть сессию. Сессия открывается командой
  `claude attach`; в Windows Terminal — вкладкой общего окна `aiflow` с названием задачи в заголовке.
- **Проекты.** У каждого своя пауза и кнопка «Дать задачу». Кнопка открывает чат с координатором проекта
  во вкладке терминала с именем проекта; если координатора нет — запускает его.
- **Доска задач по стадиям** — в каждом проекте:
  - Шаг «Мерж»: PR одобрен ревьюером и ждёт зелёный CI и слияние с основной веткой.
  - Последний шаг — «Готово». На нём стоит всякая законченная задача, в том числе вопрос с ответом
    и задача, выполненная без PR.
  - Шаги, которые задача пропустила, нарисованы бледным пунктиром.
  - Под названием задачи — когда она создана и когда последний раз менялась. Те же даты — в столбцах
    «создана» и «обновлена» у `aiflow status`.
  - У задачи на ревью написано, чем оно занято: ждёт запуска CI; ждёт CI и сколько проверок прошло;
    работает ревьюер opencode (что он читает или запускает, какой шаг, сколько токенов); идёт мерж;
    исполнитель правит код.
  - Клик по названию задачи открывает её сессию в терминале, ссылка «Ревьюер» — сессию ревьюера
    (`opencode -s <id>`). «Снять» останавливает сессии задачи и закрывает PR.
- **Расход токенов** по проектам, задачам и моделям: вход, выход, чтение и запись кэша, вместе
  с сабагентами и ревьюером opencode (его расход и цену сообщает сам opencode). У проекта — итог и оценка
  цены по тарифам API; проект в таблице сворачивается до одной строки. Свои тарифы — `prices`
  в `~/.aiflow/config.json`.
- **Статистика за 30 дней** — см. [«Статистика»](#статистика).
- **События** — лента событий очереди.
- **Настройки** (внизу страницы):
  - Кто ищет по коду в сессиях задач — `explorer` в `.aiflow/config.json`. `aiflow` — подагент
    `aiflow:explorer`. `project` — агенты и правила самого проекта: тогда aiflow о поиске не говорит
    сессии ничего, чтобы не спорить с `CLAUDE.md` проекта.
  - Модель ревьюера opencode для выбранного проекта: из списка `opencode models` или вручную как
    `provider/model`. Значение пишется в `reviewer_model` в `.aiflow/config.json` и действует
    со следующего раунда ревью.

## Статистика

```bash
aiflow stats             # задачи, созданные за последние 30 дней
aiflow stats --days 0    # за всё время
aiflow stats --json
```

Команда и раздел панели показывают по проекту:

- сколько задач уходило в «нужен человек» и по каким причинам (сбой инструмента, защищённые пути, CI,
  лимит раундов ревью и другие);
- сколько раундов ревью понадобилось до одобрения;
- время от постановки до готовности и медиану времени в каждой стадии;
- цену выполненной задачи по тарифам API.

Вопросы и обсуждения (`kind: ask`, `discuss`) не считаются. Причина ухода к человеку пишется кодом
в историю задачи (`history[].code` в `.aiflow/<id>/task.json`). У записей, сделанных до версии 0.2.107,
кода нет: он определяется по тексту причины.

## Панель как приложение

Панель ставится отдельным приложением (PWA) из Edge или Chrome:

```bash
aiflow app
```

Один раз, из любой папки. Команда включает автозапуск службы при входе в систему и открывает панель во вкладке
браузера. В панели нажмите **«Установить приложение»** (кнопка справа вверху; то же делает значок установки
в адресной строке). После этого:

- **aiflow** есть в меню «Пуск» и в списке приложений, у него своё окно и свой значок на панели задач;
- на значке — число задач, которые ждут вас;
- если служба остановлена, окно скажет об этом и откроет панель само, когда служба ответит.

В Windows рядом с часами появляется ещё и значок службы. Синий — всё идёт само, оранжевый с числом — столько
задач ждут вас. Щелчок открывает приложение. В меню по правой кнопке: задачи, которые ждут вас (щелчок
открывает чат задачи в терминале), «Дать задачу» по каждому проекту и «Остановить aiflow».

Чат задачи, как и раньше, открывается во вкладке терминала — из панели, из уведомления или из меню значка.
Выключить автозапуск: `aiflow app --remove`; само приложение удаляется в его окне (меню «…») или в параметрах
Windows. Без значка рядом с часами: `"tray": false` в `~/.aiflow/config.json`.

## Связанные задачи и несколько репозиториев

Задачу можно поставить после другой: она начнётся, когда та смержена, от обновлённой основной ветки
и получит её результат (название, PR, итог). Так ставят, например, обновление README после фичи.

```bash
aiflow after readme-update tag-colors           # после задачи этого проекта
aiflow after reader-covers common-packages/nhentai-static-covers   # после задачи другого проекта
aiflow after readme-update tag-colors --remove  # убрать
```

То же делает кнопка «После…» у задачи в панели и координатор, если вы написали «после такой-то».

Задача другого проекта считается готовой, когда она смержена и завершились workflow на коммите мержа —
там обычно публикуется пакет. Упал workflow — зависимая задача уходит в «Ждут вас». Ждать только мержа:
`"wait_workflows": false` в `.aiflow/config.json` того проекта, где публикуется пакет.

Служба одна на все проекты (`aiflow projects`), и планировщик знает соседние: имя папки и строку
«О проекте» из настроек панели. Если работа нужна в другом репозитории, он сам ставит туда задачу
(`aiflow enqueue --project <имя> --then <своя задача>`), а свою часть планирует; исполнитель начнёт
после публикации. Руками так же: `aiflow enqueue --project common-packages` из любого проекта службы.

## В чате Claude

`scripts/aiflow_mcp.py` — MCP-сервер только для чтения: инструменты `aiflow_tasks` (доска задач, все
проекты или один) и `aiflow_usage` (расход токенов по дням и моделям) со встроенным интерфейсом
(MCP Apps), который рисуется прямо в чате приложения Claude. Запись для `mcpServers` в
`claude_desktop_config.json` (Settings → Developer → Edit Config) печатает
`python scripts/aiflow_mcp.py --config`; после правки сразу перезапустите приложение: работающее
приложение при своём сохранении затирает правку файла. Тот же интерфейс без приложения —
`http://127.0.0.1:8765/app-preview?view=tasks` и `?view=usage`. В Claude Code сервер не подключается:
сессиям задач его инструменты не нужны.

### В Claude Desktop

`aiflow init` добавляет в `.claude/launch.json` две конфигурации для Browser pane вкладки Code:
`aiflow` подключается к панели службы, а `aiflow (запустить службу)` запускает службу
на переднем плане. Откройте сессию в папке репозитория, в выпадающем списке серверов на панели сессии выберите
нужную конфигурацию (или откройте Browser pane: Ctrl+Shift+B / Cmd+Shift+B) и закрепите панель
рядом с чатом. Вторая конфигурация содержит пути вашей машины: после обновления плагина
перезапустите `aiflow init`, а в общий репозиторий этот файл лучше не коммитить. Если в
`launch.json` есть комментарии, init его не трогает — добавьте записи вручную по образцу из
`aiflow init` в чистом репозитории.

Остановить службу вместе с панелью — `aiflow down` (продолжить — `aiflow up`). Пауза очереди (`aiflow pause` или кнопка в панели) не трогает работающие
сессии, только не даёт стартовать новым. Сами фоновые сессии останавливаются в `claude agents` (`Ctrl+X`)
или `claude stop <id>`.

Строка состояния в Claude Code (`~/.claude/settings.json`):


## Команды

| Команда | Назначение |
| --- | --- |
| `aiflow init` / `doctor` | Подготовить репозиторий / проверить среду; `doctor` называет и настройки, оставшиеся от умолчаний прежних версий |
| `aiflow status [--json]` | Состояние очереди |
| `aiflow stats [--days N] [--json]` | Статистика: причины ухода к человеку, раунды ревью, время по стадиям, цена |
| `aiflow approve <id>` | Одобрить план |
| `aiflow retry <id>` | Повторить задачу в `needs_human` |
| `aiflow allow-path <id> <glob>…` | Разрешить задаче защищённые пути (только человек; задача в «нужен человек» продолжит работу) |
| `aiflow amend <id> <текст>` / `--file F` | Дополнить идущую задачу: правку получит её текущая сессия (планировщик или исполнитель, даже посреди работы — через хук); в панели — кнопка «Дополнить». Обычный комментарий в PR после начала реализации работает так же |
| `aiflow model <id> [--planner M] [--worker M] [--planner-effort E] [--worker-effort E]` | Задать задаче модель и effort (`fable`, `opus`, `sonnet`, `haiku` или полный id; `default` — как в проекте). Оркестратор делает это сам, когда вы называете модель: «план пусть делает fable» |
| `aiflow cancel <id>… [--keep-pr]` | Снять задачи на любой стадии: остановить их сессии, закрыть PR (ветка остаётся); в панели — кнопка «Снять» |
| `aiflow pause [причина]` / `resume` | Пауза очереди |
| `aiflow up [--open] [--autostart\|--no-autostart]` | Запустить службу, добавить в неё текущий проект |
| `aiflow down [--no-autostart]` / `aiflow stop` | Остановить службу и панель |
| `aiflow projects` / `forget [путь]` | Проекты службы / убрать проект |
| `aiflow ui [--open] [--detach]` | Открыть панель (окном приложения с `--open`) |
| `aiflow chat` | Чат с координатором проекта в этом терминале; вкладка названа именем проекта и не переименовывается |
| `aiflow tick` | Один проход вручную |
| `aiflow enqueue` | Поставить задачи (JSON со stdin; использует intake) |
| `aiflow report`, `review`, `reply` | Команды для агентов |

## Как это устроено

Состояния задачи: `new → planning → plan_check → plan_review → approved → in_progress → ready → in_review → merged`,
плюс `needs_human` и `cancelled` (`plan_check` — план проверяет ревьюер, `approved` — план одобрен, задача ждёт слот исполнителя). Каждый переход — проверяемый сигнал: отчёт сессии
(`aiflow report`), метка PR, состояние сессии из `claude agents --json`, статус PR.
`concurrency` ограничивает сессии планирования и реализации; ревью идёт поверх лимита:
до `review_concurrency` PR сразу, если у них нет общих файлов. Rate limit ставит очередь на паузу на
`rate_limit_pause_minutes`, красный `master` после мержа — до починки. Причины паузы независимы,
и пауза останавливает не только запуск сессий, но и мерж.

Ревью плана. Код ревьюер сверяет с планом и решений плана не оспаривает, поэтому ошибку в самом плане ревью кода
не ловит. До того как план увидите вы, его проверяет тот же ревьюер opencode (другая модель, чем у планировщика):
существуют ли названные файлы и функции, покрыты ли критерии приёмки, перечислены ли все места, где используется
изменяемый интерфейс, делает ли план то, что просили, соблюдены ли правила проекта. Замечания он пишет комментарием
в PR. Планировщик один раз отвечает на них — исправляет план или возражает, — и только после этого приходит
уведомление «план готов», уже с итогом ревью. Ревью советующее: план попадает к вам в любом случае, в том числе
если ревьюер не запустился или планировщик не ответил за `plan_check_wait_minutes`. Настройки в `.aiflow/config.json`:
`plan_check` — `advisory` (по умолчанию) или `off`; `plan_check_rounds` — сколько раз ревьюер смотрит план
(по умолчанию 1). Свои инструкции ревьюера плана — `.opencode/aiflow-plan-reviewer.md` (по умолчанию
`templates/plan-reviewer.md` плагина).

Разбиение на несколько PR. Если задача велика для одного PR (больше примерно 1500 строк diff или несколько
независимых частей), планировщик пишет об этом в плане и предлагает части. Решаете вы: ответьте в PR или в чате
задачи «разбей» либо «оставь один PR». При разбиении задача остаётся первой частью — с тем же id, веткой и PR,
план в нём сужается до этой части, а название задачи меняется на название части. Остальные части планировщик ставит в очередь сам (`aiflow enqueue --split-of <id>`):
в текст каждой он переносит решения исходного плана, которые её касаются, а в `depends_on` — части, после мержа
которых она стартует. У каждой части свой план и свой PR; дизайн (`ui`) и выбор моделей переходят к ней от исходной задачи.

Ревью fail-closed: неизвестная серьёзность замечания считается блокирующей, обрезанный дифф
без подтверждения ревьюера блокирует, изменения защищённых путей блокируются без вызова
модели. Красный CI возвращается worker'у до ревью и раунд не тратит (не больше `max_ci_fixes` раз подряд).
Отсутствие проверок CI при наличии workflow — ошибка, а не «прошло». У задачи без плана контракт
для ревьюера — её текст и указания планировщика. Отчёты сессий проверяются: PR должен
быть открыт из ветки `ai/<id>`.

Ответ ревьюера не по форме. Если ревьюер отработал, но закончил ход без ответа (например, на отклонённом
вызове инструмента) или ответил не одним JSON-объектом, aiflow не начинает ревью заново, а просит ту же
сессию opencode дослать ответ по форме: всё прочитанное уже в её контексте. Ответ, который отличается только
названиями ключей (`findings` вместо `comments`, `issue` вместо `text`), принимается как есть. Ответ без списка
замечаний одобрением не считается.

Модель исполнителя выбирает оценка планировщика (`worker_model` и `worker_effort` в `.aiflow/config.json` —
словарь по уровням или одна строка на все задачи):

| Оценка | Когда | По умолчанию |
| --- | --- | --- |
| `trivial` | лёгкая задача без плана: механическая правка по точным указаниям планировщика | Haiku, effort `high` |
| `simple` | простая задача без плана или план, после которого осталась рутина | Sonnet, effort `medium` |
| `complex` | план, реализация которого сама сложна | Opus, effort `worker_opus_effort` (`medium`) |

Модель для отдельной задачи задаёт `aiflow model <id> --worker M`.

Вместе с планом планировщик пишет заметки для исполнителя (`.aiflow/<id>/notes.md`): где что лежит в коде,
сигнатуры, рабочие команды сборки и тестов, подводные камни. Исполнитель читает их первым и не повторяет
поиск планировщика. В PR заметки не попадают.

## Тесты

```bash
python -m unittest discover -s plugins/aiflow/tests
```

Тесты гоняют очередь (`Dispatcher`) и раунд ревью (`review.py`) на подделках `claude` и `gh`:
ни сеть, ни модели не нужны. CI репозитория (`.github/workflows/ci.yml`) запускает их в Windows и Linux
на Python 3.9 и 3.13 и проверяет код линтером: `python -m ruff check plugins` (правила — в `ruff.toml`).

## Обновление

Что изменилось в версиях и что сделать при переходе со старых — в [CHANGELOG.md](CHANGELOG.md).
Настройки, которые появились в новой версии, служба дописывает в `.aiflow/config.json` сама. Значения,
которые были умолчаниями прежних версий, она не меняет — вы могли выбрать их сами, — а один раз сообщает
о каждом событием в панели; `aiflow doctor` перечисляет их при каждом запуске.

## Что проверить при первом запуске

- Монитор стартует в фоновой сессии оркестратора по первому `/aiflow:intake`: первая строка
  `aiflow status` без пометки «монитор не запущен», панель открывается (при `notify: important`
  в сессии появится и строка `[aiflow] монитор запущен; панель: …`). Мониторы плагинов работают только
  в интерактивных сессиях; фоновая сессия интерактивная, но это главное, что надо увидеть
  своими глазами.
- Тестовая задача проходит путь до `ready` без зависаний на запросах разрешений.
- AI-ревью появляется в PR, после approve PR мержится в `master`.

## Ограничения

- Agent view в research preview; при смене флагов CLI правки нужны в классе `Claude` в `scripts/aiflow.py`.
- Фоновые сессии локальные: выключение машины их останавливает; после `/aiflow:resume` монитор их возобновит.
- Deny-правила защищают от случайностей, а не от злого умысла. В режиме `self` агенты работают
  с вашим `gh`, и смержить в обход ревью им мешают только deny-правила (`gh pr merge`, `gh api`)
  и инструкции; жёсткая граница — режим `bot` с обязательным одобрением в защите ветки.
- На Windows монитор запускает `bin/aiflow` через ту же оболочку, что и Claude Code (Git Bash);
  из PowerShell используйте `bin/aiflow.cmd`.
